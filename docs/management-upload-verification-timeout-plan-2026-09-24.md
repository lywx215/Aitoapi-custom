# 管理 API 上传验证超时修复方案

日期：2026-09-24。来源：Gemini Manager 任务“核实 Aitoapi 多服务器导入状态”。

最新行为修订：上传与模型验证已分离。客户端可在 import 或版本化 replace 传 `verify:false`，只保存凭证并启用，不调用验证器；独立 `/accounts/{id}/test` 只读。省略 verify 保持原 API 行为：import 保存并启用后验证，replace 先验证候选并保留原管理标记。上传成功结果为 `stage:uploaded` 和提交时双版本，不能作为模型验证证据。此修订优先于下文历史流程；尚未部署或操作线上账号。

状态：已依据当前源码审核并修订；用户随后授权实施，第 3.6 节/T4 的 Aitoapi 远端上传回执已完成实现与离线验证，并授权与独立账号管理页面统一提交、推送。页面超时根因项尚未实施；线上部署结果另行确认。429 熔断策略另行处理。本方案不追加业务审批、业务表或整台服务器锁。

审核基线：本地 HEAD `0ac309c693a70d95c26642ae3b76ce3021aaa784`（`fix: strengthen management version evidence and recovery contracts`）。审核开始时唯一工作区差异为本方案尚未跟踪；该提交不代表线上部署版本。第 7 节记录方案审核阶段，第 8 节记录之后的实施阶段，未调用真实模型或远端管理接口。

精确边界：`adapter.start()` 在主页面 `domcontentloaded` 后返回，不代表 iframe 或 Build App 已就绪。25% 循环依次等待 `inspect()`、检查连接、执行 `wake()` 和轮询间隔；连接已建立且 `inspect()` 返回身份未确认时，会立即报 `identity_unconfirmed`。旧 WIZ 字段缺失本身不足以解释十分钟超时，需优先区分连接未建立、页面检查/唤醒未完成，以及进度回调等待。以上定位以线上代码与审核基线一致为前提。

9 月 22–23 日的本地真实诊断发现 `WIZ_global_data.oPEP7c` 缺失，仅是身份适配的已知问题，不等同于本次线上根因。后续业务成功时凭证版本已变化，也不能倒推原导入版本验证成功。

## 2. 预期流程

首次 import：凭证保存并关联远端账号及上传回执 → 打开指定账号的独立验证页面 → 启动 Build App → 确认当前登录身份和内部连接 → 对目标模型生成 → 校验响应及版本 → 按现有 import 流程启用并保存提交版本。

失败时保留已创建的账号、上传证据及具体阶段；再次操作查询旧任务，终态后对已有账号复验。`test` 成功只返回验证结果及复核版本，不自动启用；`replace` 成功也保留原禁用状态。恢复服务由现有调用方按启用策略携带凭证/状态双版本执行 `PATCH enabled=true` 并读回，遇到版本变化或人工停用则停止自动恢复。来源凭证变化时走既有 replace，避免重复 import。

## 3. 修复设计

### 3.1 先取得足以定位的阶段证据

- 核对线上部署提交，读取北京时间 11:17–11:28（UTC 03:17–03:28）日志。本地 zeaburcli 有只读 status/runtime logs 能力，但目前仅登记 `cliproxyapi`，缺 Aitoapi 的 project/service/environment 映射；现有 runtime 查询也未提供历史时间范围参数，`--limit` 只是截取返回结果。先确认目标映射、读取权限和日志保留范围，不能把其他服务日志用于归因。缺少日志时先完成代码观测和离线复现，不把猜测写成根因。
- 跟踪 `taskId / accountId / authIndex / verification requestId`、各阶段耗时、最后完成阶段、当前等待条件。
- 记录导航状态、页面 origin 与规范化路径（不含 query/hash）、已识别启动控件、iframe 初始化、身份确认结果、WebSocket 尝试/连接/断开、安全的网络失败类型及 HTTP 状态。
- 网络错误注明是页面初始化还是目标模型响应；只有对应生成请求的状态才能填 `upstreamStatus`。
- 在错误产生处记录白名单错误类型、固定原因码和经过脱敏的调用位置；外部库原始 message/stack/cause 必须统一脱敏和限制长度，不能直接递归序列化。公共任务只输出结构化安全字段。不能记录 Cookie、请求/响应全文、授权头、localStorage、任意页面 console 文本或完整 DOM；隔离 WebSocket 的 `/verify/<nonce>` 路径及代理凭据也必须遮蔽。页面事件通过受控诊断回调采集，并校验所属 page/frame 与本次请求归属。
- 阶段快照归本次 job 所有，在每个异步等待前更新；`verify()` 外层超时/取消竞争直接从该快照构造结果，不能只在 `execute()` 的 catch/finally 中追加，否则调用方可能先收到没有阶段的超时。记录排队与清理等待；当前十分钟从 `verify()` 入队前开始，包含这些耗时，继续保留这个预算语义。
- 超时或取消返回时先附加最后阶段快照，后台继续可靠清理。验证错误与清理错误分别记录，清理失败不覆盖原始错误。后续清理结果通过关联日志记录，不把已经返回的失败任务改成成功。
- 当前 `execute()` 清理没有单独截止时间；`closeTimeoutMs` 只限制整个 verifier 的 `close()`。若自有 context/browser 的关闭永不完成，`tail` 会一直占住，后续验证可在排队中超时。补有界清理诊断和仅针对自有资源的恢复路径；未确认资源释放时不得单纯放行下一验证。增加清理卡住时后续任务能明确报告等待原因的用例。

### 3.2 页面启动复用现有实现

- 比较 `BrowserManager` 的 Continue/Launch、iframe 初始化及唤醒逻辑与 `VerifierBrowserAdapter.wake()`。
- 当前验证器只匹配精确英文按钮名；业务路径会识别控件内部 Launch 文本。这是已确认的实现差异，尚未证明是线上阻塞点。先用实际控件样本复现，再提取确有复用价值的页面启动小函数，接收 page 和取消信号，供两条路径调用；不复制整个 BrowserManager，也不顺带改业务调度。保留不点击通用 Continue、登录或条款确认控件的约束。
- 以实际页面结构选择对应控件及 frame，覆盖图标与文字组合、延迟渲染、控件替换和语言变化。重复循环只在页面需要时点击，避免不断点击已启动应用。
- 沿用现有浏览器可执行路径、代理和平台适配。只补经确认影响启动的配置差异。
- 保留独立验证上下文，结果归属仍是本次指定账号，资源清理不关闭业务浏览器。

### 3.3 修正身份适配

- 将当前单一 WIZ 字段读取整理为可测试的身份解析函数。
- 在真实 Google 第一方页面核实当前可用的会话身份信号；可兼容旧 WIZ 字段及已验证的新来源，不把某一个旧字段存在作为唯一条件。
- 确认的是当前登录会话；不直接拿待上传的 accountName、普通页面任意邮箱或其他账号的成功结果作为登录证明。
- 身份未就绪与身份不匹配分别反馈。若已连接但页面身份仍初始化，可在总体预算内给一个有界身份等待阶段，期间不得发送生成请求；已识别登录要求、账号不符等明确结果时直接报告具体原因。当前实现是已连接即检查身份并失败，调整等待语义需要新增覆盖，不能仅替换字段读取函数。
- 不通过降低身份检查来把超时改成成功；这用于避免验证结果写错账号，不新增用户操作步骤。

### 3.4 核对隔离 WebSocket 协议

- 对照 `scripts/client/build.js`、`installIsolation()` 和 `VerifierTransport`，核实实际 URL、authIndex 获取时序、iframe 消息以及重连行为。
- 当前 `scripts/client/build.js` 默认使用 `ws://127.0.0.1:9998?authIndex=...`，与隔离脚本匹配。仅在部署脚本或实际连接证据证实差异后扩展地址兼容；保留 nonce、索引、请求及 attempt 绑定，不能通过放宽 loopback 规则来猜测修复。
- 明确区分未发起连接、握手失败、索引不匹配、连接后断开、身份未确认，避免统统等待到全局超时。
- 当前 `connected` 只会 resolve；生成前没有 `rejectResponse`，部分监听/握手错误不会传播给等待者。增加贯穿初始化与生成的失败信号；握手拒绝记录安全原因，并防止错误候选连接覆盖已认证连接。
- 当前 transport 保留首个 `socket`，关闭后不清空，后续连接仍被拒绝，不能宣称支持重连。第一步采用明确失败并清理的行为；只有证据要求恢复时才增加生成前有界重连，并重新验证身份和连接归属。模型请求已发出后不自动重放，避免一次验证产生重复调用。
- 保持现有总体超时作为兜底；本轮不以单纯加长等待时间解决问题。阶段等待值使用现有配置或内部默认，不新增用户必填配置。

### 3.5 任务契约和已有账号恢复

- `ManagementTaskService` 当前将未识别进度阶段折叠为 `verifying`，并在 `_verification()` 中把未列出的失败原因折叠为 `failed`（包括 `initialization_failed`、`connection_closed`、`protocol_mismatch`、`cleanup_failed`、`empty_response` 等）。保留现有 stage/错误码语义，在可选诊断对象中增加 `phase / waitingFor / elapsedMs / reason` 等白名单字段，使任务查询能区分排队、检查会话、启动应用、等待连接、模型生成及清理。
- 保留原 taskId、状态、错误码和结果字段，新增字段可选。修复涉及 `VerifierSupport → ManagementVerifier → ManagementAccountService → ManagementTaskService` 的错误传播全链路，不能只改日志。
- 同步检查 `ManagementSupport.safeError`、任务结果 `_verification()` 的字段白名单及 OpenAPI 的 `additionalProperties:false`。`onProgress` 当前只转发 stage/progress，新诊断对象需要显式转发、脱敏、持久化与读回；公共 error 继续只保留稳定 code/message。避免以 250ms 轮询频率刷任务文件，只在阶段或等待状态变化时持久化，终态保留最后快照。
- import 已创建账号但验证失败时，保留 accountId/index；不重复创建账号。超时本身不标记凭证永久失效。
- 复验沿用 `/accounts/:id/test`；凭证更新沿用 replace；成功结果继续包含实际凭证/状态版本，不能将旧结果应用到新版本。
- 已核实：import/replace 返回实际提交版本，test 返回验证后复核版本；test 不修改启用状态。调用方恢复启用时使用该版本对执行 CAS；启用后的新 stateVersion 单独读回，不覆盖历史验证结果。失败不自动强制启用。
- Gemini Manager 联动项交由其项目：显示“已上传，验证失败”和具体阶段；已有绑定再次上传应按版本走 test/replace，并通过组合测试确认，不另建上传通道。

### 3.6 客户补充：上传、验证和运行状态分别管理

客户明确要求区分上传成功与验证成功，以便持续管理凭证所在服务器。此要求同时适用于验证超时和后续 429 停用；必须修改结果契约与本地展示，不能只替换“失败”文案。

**三项独立事实：**

| 维度     | 状态与依据                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 凭证上传 | 未上传、上传中、已上传、上传失败、结果待核对；以该次凭证写入提交回执为依据，带本地来源版本、远端凭证版本、远端账号和任务关联 |
| 模型验证 | 未验证、验证中、验证成功、验证失败、验证结果待核对；带目标模型、被验证的凭证版本、时间及具体原因                             |
| 远端运行 | 已启用、待启用、已停用、已归档、状态待核对；保留停用原因、HTTP 状态和最后核对时间，与服务器目录自身的 active/inactive 分开   |

绑定服务器、角色和远端账号独立保留。验证超时、429、网络异常和手工停用均不能自动清除绑定或把已确认上传改成未上传。确认停用并解绑完成后才解除本地绑定，历史继续保留。

**实际提交点必须区别处理：**

- 现有 import：`store.create` 成功后凭证已经提交，随后验证失败应为“已上传 / 验证失败”，不是上传失败。此时即持久记录上传回执，终态失败保留该回执。
- 现有 replace：候选凭证先验证，`store.replace` 成功才表示新版本上传提交。验证失败时应为“新凭证未更新 / 候选验证失败 / 原凭证仍在该服务器”。已有 accountId 不能证明本次新版本已上传。
- 202/已受理/taskId 只证明任务受理；请求超时且无提交证据应为“上传结果待核对”，不能自动重传。
- 当前查询到的账号版本可能已被其他操作修改。上传提交时的版本与最近观察版本分别保存，不能用后来的当前版本补造原请求回执。
- 复验成功按被验证版本记录，不抹掉已有上传记录。验证成功后发生 429，应显示“已上传 / 上次验证成功 / 当前因 429 停用”，不宣称当前可用。
- 再次采集后分别显示“本地来源版本”和“该服务器已上传来源版本”；Pro/Flash 独立比较。历史验证成功保留，但应标明仅对应旧版本。
- 管理队列 429、模型验证 429、业务运行 429 分开归因；不能一律写额度耗尽。远端返回的 quota_exhausted 可如实显示，但深层原因需原始安全诊断支持。

**契约与持久化：**

- 在现有 task item 增加独立可选的上传提交回执，现有 `result` 继续承载验证结果，保持旧调用方兼容。新增上传回执回调不能复用 `item.committed()`：该方法会立即把整项标成成功，导致后续验证失败被当作提交后附加错误。上传回执与任务最终成功必须分别记录，进度和错误回调不得覆盖上传回执。
- **存储事务不能只落在 tasks.json。** 当前 `CredentialStore` 使用凭证文件、`credentials.json` 与回滚 journal，`ManagementTaskService` 独立写 `tasks.json`；现有代码没有跨两者的原子事务。仅在 `store.create/replace` 返回后追加任务字段，仍存在凭证已提交而回执丢失的窗口。T4 必须包含 `src/storage/CredentialStore.js` 与存储故障恢复测试。
- 建议使用任务创建时已持久化的 taskId + item 序号作为稳定操作关联，将非秘密提交证据（操作关联、kind、accountId/index、实际提交的 credentialVersion/stateVersion、提交时间）写进现有凭证元数据，并与凭证变更由同一次 `_commit`/journal 提交。任务回执从该证据生成；重启只补已证实的回执，不自动重跑验证或启用。回执按操作保留，不能只保存一个会被后续 replace 覆盖的“最近操作”，保留期至少覆盖任务核对窗口。
- 当前服务端没有本地来源版本字段。该版本由 Gemini Manager 在派发时固化，并按服务器 origin、taskId、item 及 clientRef（仅 import 已支持）映射到远端回执；不要从后来更新的本地凭证反推原来源版本。replace 的关联使用 task/item，不假设其支持 clientRef。若需要额外请求字段，应显式更新请求白名单及接口契约。
- 覆盖凭证提交前退出、journal 未完成、凭证提交后任务回执写入前退出、回执后验证失败/取消等断点。任务构造器当前会将运行中任务标成 interrupted 并清理私有输入，恢复关联必须来自预先持久的非秘密证据，不能依赖私有输入仍存在。未证明关联的同邮箱账号只作为待核对候选，不能用后来读到的版本补造原请求回执。
- Gemini Manager 的 `applied_source_version` 当前被验证失败分支清空，不能继续承担上传和验证两种含义。上传证据与验证证据分别持久化，终态清除检查点也不丢失。
- 优先复用现有槽位字段、任务结果和账号历史，不新增业务表。实施前明确字段语义；若现有字段无法无损承载，列出最小兼容字段调整，不把持久业务事实只存在面板内存或将已结束检查点长期留作存储。
- 历史数据缺少上传版本证据时显示“远端账号已关联，上传版本待核对”；不批量猜测、改写历史成功记录。
