## 4. 证据缺口

- `platform.jsonl` 的 CPU、内存和网络有效点为空；resource limit、termination reason 及 `oom.confirmed` 为 null；runtime log entries 为 0。**零个日志条目、空指标、null OOM 状态都表示未知，不能写成“CPU/内存正常”“没有 OOM”或“没有断连”。**
- `environment.jsonl.local` 的 CPU / RSS / event loop 是压测客户端进程和本机数据，不能替代服务器 / 浏览器指标；本机网络原生计数标为不可获取。
- 安全管理 usage 只有最终账号和最终结果，没有 attemptCount、每次尝试账号、close cause 或 provider 详情。它能定位“哪组最终结果集中在同一账号”，不能证明请求只调用过那个账号。
- status `ready=true` 是抽样时存在可用条件的总体判断，不保证每个账号、每个模型路由或全部并发请求可用。五秒采样可能漏掉短故障。
- usage 是最新优先、实时 offset 分页。600 条窗口可去重关联，但并发完成时页面会位移；遗漏与无法关联的请求须保留 coverage，而不是算作没有错误。
- 本记录尚不提供“稳定最大并发”。通过探索档也有样本量和热状态限制；后续还需六种负载、非流式对照和持续运行验收。

## 5. 后续改善建议与验收方向

1. **先让故障原因可区分。** 在所有入口生成请求 ID 后立即返回同一响应头，覆盖 readiness 之前的 503；诊断保留枚举式 queue close cause、WS close code、connection generation、context closure initiator 及 attempt 时间线。详细事件仍只在 DEBUG 下输出；公开错误不带用户正文、账号名称或凭证。先验证日志导出能真正读到事件，再重复失败边界，避免只开启 DEBUG 却没有可用证据。
2. **加入有界调度。** 为每账号 active fetch 设置可配置并发上限和服务总在途 / 排队限制，以 token 或输入字节数纳入 admission。长输入等待时使用有界队列、总 deadline 和公平调度；超限返回可解释的 429/503 与 Retry-After。具体每账号上限应通过 5 / 10 / 20 等小阶梯比较选定，不能用本次总连接数直接推出。
3. **明确池大小与预热上限。** 分开暴露目标 ready pool、实际 live、initializing、draining 和 peak；限制替换时允许增加的 context 数量。对达到 usage 阈值的账号提早预热目标，稳定接力后停止新 admission，并排空旧 attempt 后再关闭。保留 busy queue 保护，给所有强制关闭路径一致的 reason 和在途计数。
4. **拆开首字等待和输出后空闲预算。** 先记录排队 / 预热 / dispatch / headers / first byte，验证 60 秒失败究竟来自哪段；首字前可在总预算内使用独立超时，首字后保持 idle timeout。单纯增加所有超时只会延后排队失败，不能自动增加吞吐。
5. **限制共享传输堆积，减少输入副本。** 服务器发送端依据 bufferedAmount 与发送完成回调控制入队；浏览器保留现有回传背压并增加公平性和队列水位。输入按 action 设置大小上限，减少 rawBody、解析对象和序列化字符串同时保留；将输入、WS 缓冲、浏览器 fetch、输出 budget 分别计量。
6. **谨慎处理断连重试。** 只有正文尚未提交、无工具副作用、旧 attempt 关闭得到可靠确认且总预算仍有余量时，才评估换账号重试；不能盲目重放一个“可能已发送”的请求。HTTP 200 已写出后的故障继续作为不完整响应，不能用重试覆盖已发送正文。
7. **修复计数 action 兼容性。** `countTokens` 保持顶层 contents 和 generateContentRequest 两种受支持形式；生成专属字段注入只用于对应 generation action。回归同时验证原生 countTokens、流式及非流式 generation，不把压测 wrapper 绕过当作服务端修复完成。
8. **复测使用同一合格定义。** 对每个改善分别比较完整成功率、P95、首字 P95、最终账号集中错误、临时 context 峰值和累计账号不可用数；完成 ≥10 分钟与足够样本的持续验证后，再给稳定容量结论。服务器 CPU / 内存尚未取得时，只能报告响应能力，不能发布已确认的资源瓶颈归因。

本轮未实施上述服务改善，也没有为了恢复测试成绩重新启用 index 15 / 26。最终报告应保留测试结束时实际账号状态，并将缺失的禁用原因作为后续诊断项。

### 6.2 404、502、503、504 的账号分布

- **404 分散在不同账号和阶段。** 10k / 2k 为 C250 的 index 19；10k / 4k 为 C50 / C250 / C300 的 index 32 / 45 / 54；30k / 2k 为 C50 / C250 的 index 57 / 72。公开信息均只有 `upstream http error`。不同输入/输出长度下同一模型仍有大量成功，因此这些样本不能证明模型名称整体失效。两个负载的 C50 都因单个 404 取得 49/50，而非出现大面积超时；需复测足够样本再判断该档容量，不能只由一次 404 定义硬上限。
- **502 批量故障目前只明确见于第一种负载的 index 9。** 后两种完整探索波次未复现相同 41 条集中失败，但没有关闭原因日志，不能推断某项关闭竞态已经自然修复。
- **503 在较高并发下持续存在。** 10k / 4k 的 C200 / C250 / C300 为 2 / 4 / 5 个；30k / 2k 的 C100 / C150 / C200 / C250 / C300 为 1 / 2 / 2 / 3 / 4 个。都缺乏客户端请求 ID；能确认无健康连接错误出现，不能分配到同一账号，也不能仅凭同时的 ready context 总数解释具体请求为何没有被调度。
- **504 在长输出负载明显增加。** 10k / 4k 从 C100 开始出现 16 个，然后 C150 / C200 / C250 / C300 为 60 / 84 / 109 / 134 个；最终账号按阶段从 index 34 推进到 56。30k / 2k 同档为 7 / 22 / 16 / 40 / 42 个，最终账号从 index 60 推进到 82。各账号分组仍有“初始约 60 秒、后续较晚一批加上预热 / 等待时间”的阶梯完成现象，和第 3 节的 idle timeout 路径相符，具体等待发生在服务器、浏览器或上游尚未确定。

另外，30k / 2k 的 **C150 出现 14 个 HTTP 403**，全部最终账号为 **index 65**，该账号本波次没有合格请求。完成时间为 14:16:44.769–14:17:14.819，公开消息仍只有 `upstream http error`；下一 C200 波次，同一个最终账号 index 65 又有 **26 个合格请求**。`RequestHandler._autoDisableAccountForStatus` 对带模型名且未明确 accountLevel 的 403 会保留账号启用，代码没有在该分支把它当作账号全面禁用；因此启用总数不变与代码规则相符。现有数据不能证明这 14 条的具体 provider 原因，也不能把它们描述成账号永久失去模型权限。没有 attempt 详情时，不应推断这些请求已经尝试了多少次换号。

### 6.4 对后续改善和复测的约束

后续按同一并发、同一输入 corpus、相同账号就绪状态交替测试 10k / 2k、10k / 4k、30k / 2k，记录每次实际 ready connections、inFlight、initializing/draining 和首字前时间线。每账号并发闸门应同时评估长输出和短输出，不能只限制累计 40 次轮换计数；临时上下文也需要硬上限和完整计量。为 403 / 404 保存安全枚举 provider status / code 及内部 retry 次数，才能区分瞬时提供方错误、模型权限和服务转换问题。

这三种负载的全部高并发结果仍低于 99% 标准。第一组 C100 的 99/100 是单波次门槛通过，后两组 C50 的单个 404 又说明孤立事件会影响小样本门槛；最终稳定容量必须使用边界重复与持续验证，不能拿某组一次较好的 C300 合格率替代验收。

### 7.1 30k / 4k 的 C200 极端失败波次

`explore-in30000-out4000-sse-c200-0044` 开始于 **14:28:39.539（06:28:39.539 UTC）**，结束于 **14:29:17.976（06:29:17.976 UTC）**。200 个请求中只有 **7 个合格（3.5%）**，其余 **193 个均为 HTTP 503**，消息为 `No healthy account connection is available.`。7 个成功请求全部关联到最终账号 index 91；193 条客户端请求 ID 均为 null，不能为它们指认具体账号。

波次内的七次管理快照全部 `readiness=true`、`isSystemBusy=false`、`enabledAccountCount=88`、浏览器连接正常，uptime 连续增长。实际已登记上下文数前两次为 1 / 2，随后为 3；不能省略前两次采样而称全程始终三个上下文。193 个 503 集中在 **14:28:51.427–14:28:51.688** 完成，相差约 261 毫秒，耗时 11.86–12.09 秒；相邻上下文快照为 14:28:48.089 的 2 个和 14:28:53.087 的 3 个，无法确认失败瞬间恰好几个上下文。7 个成功请求则在 14:29:04.856–14:29:17.975 完成。

该波次总耗时 P95 仅为 **12.082 秒**。这主要处于大量快速失败结果的分布中，**不是性能突然改善**：合格率已经跌到 3.5%。仅监控 P95 或非模型健康探针会漏掉这种服务退化。没有出现连续 60 秒 readiness=false，所以本次既定自动停止条件未被触发；条件未触发不代表生成服务没有严重失败。

### 7.2 已确认的源码定义差异

`ManagementAccountService.status()` 的 `ready` 定义为：浏览器进程连接、全局 `isSystemBusy=false`，且任意一个账号符合 enabled、未被 management maintenance 阻塞、WebSocket `readyState=1`。`readiness()` 的 `model_connection` 检查直接复用这个布尔值，**没有传入本次模型，也没有读取每账号路由状态**。

实际 `RequestHandler._selectRequestAuthIndex()` 还会排除不在 availableIndices 的账号、账号不可用、WebSocket crash loop、账号 cooldown、该模型 cooldown，以及多上下文模式下的 `usageExhausted`。因此“至少一个 enabled 账号的 WebSocket 打开”和“存在可接收 gemini-3.8-flash 的账号”是不同条件。这是已确认的接口定义差异，足以解释 readiness 的观测与生成错误可以并存；它尚不能证明本波次 193 个失败具体触发的是哪一个路由过滤项。

`_warmStandbyForModelUnlocked()` 同样过滤上述候选状态，而且满池时需要找到可替换来源、避开已 pending close 的来源；没有合格候选会直接返回 false。恢复后重新调用 `_selectRequestAuthIndex()` 仍无候选时，生成入口会返回本波次观察到的 `No healthy account connection is available.`。上下文数为 3 也不能单独证明这些候选规则已满足。

### 7.3 累计 40 次轮换与周期转换的相关证据

发生 C200 之前，30k / 4k 的 C150 有 64/150 合格，另有 41 个 403、43 个 504、2 个 503；其中 41 个 403 全部最终账号为 index 90。阶段内全局当前账号由 85 推进到 90、91，之后在 **14:27:48.026（06:27:48.026 UTC）**的快照回到 index 2。C200 七个成功最终属于 index 91，随后 C250 的 133 个成功以及 113 个超时重新分配到 index 2 / 3 / 4 / 5 / 6 / 7 和 index 91，表现出账号轮换重新从头开始的现象。

从当前测试可关联 usage 计数看，多数遍历过的账号累计在 40 或 41 条附近；代码默认 `switchOnUses=40`。`_rotateAccountAfterUsage()` 仅在来源 usage exhausted 且 `inFlight=0` 后执行，并在没有候选时调用 `_resetExhaustedUsageCycle()`；新请求的 standby 候选扫描本身不负责全周期重置。这些规则与“最后一批在途请求尚未排空、已有 WebSocket 仍打开但旧 usage 状态不可调度，直到周期转换后再恢复 admission”的解释相符。

**上述是优先验证的假设，尚未确证**：没有实际运行时的 usageCount / usageExhausted、pendingUsageRotations、inFlight、cooldown / crash-loop、初始化中对象和 cycle-reset 事件。管理 usage 是最终账号，且还可能漏掉前期流量、内部重试和其他客户端请求，不能把 40/41 条客户端计数直接等同服务内部计数。也不能将全局 current index 回到 2 的快照当作精确的周期重置事件。

后续 C250（14:29:18.619–14:31:04.084）已恢复到 **133/250 合格**，错误为 113 个 504 和 4 个 503，证实 C200 的 193 条 503 不是此后每个请求都持续失败的状态。但 53.2% 合格率仍不达标，也不证明任何服务代码问题已经被修复。其公开上下文计数再次达到 7，说明恢复依然伴随额外上下文。

### 7.4 后续接口与监控改善方向

- 增加与实际路由共用判断的模型就绪信息：当前模型的 eligibleConnections、被 usage exhausted / cooldown / crash loop / maintenance 排除的数量、可预热候选数量和排队容量。保留基础存活检查，同时不要再把通用 WebSocket 条件作为完整模型 admission 的证明。
- 周期转换明确暴露“停止新 admission、排空、预热、重置”的阶段与耗时；保证候选为空时请求可在总 deadline 内等待一次有界的周期恢复，而不是全局 ready 为真时批量快速返回含糊 503。是否允许提前重置使用次数必须结合轮换目的与在途安全另行设计，不能在压测中直接取消阈值。
- 压测安全监控除现有 readiness 连续失败规则之外，另列“模型完整成功率骤降 / 连续无可调度账号”事件；这是后续需要明确阈值的改善项。本次运行不修改原方案的停止规则，也不因为未触发该规则而将 193/200 失败判为环境正常。
- 把 503 入口的请求 ID 和安全 rejection reason 写入可关联记录；返回账号 index=null，避免用全局 current account 误导定位。

### 11.2 部署同版源码的计时与错误映射

下表核对当前未修改的相关源码；这些文件与部署提交 `4cb7756` 对应。`ConfigLoader.js` 的 60 秒和 300 秒是代码默认值，当前平台没有暴露相关环境变量的有效值，不能把默认值当作已独立读到的线上配置。

| 层次 | 计时开始 / 更新 | 默认预算与触发行为 | 本地源码位置 |
| --- | --- | --- | --- |
| 前有效输出的绝对预算 | 以 `req.__generationStartedAt` 为起点；首次响应提交后清除 | `generationPreoutputTimeoutMs` 默认 300,000 毫秒；到期产生 `preoutput_timeout` / 504 | `src/utils/ConfigLoader.js:72`；`src/core/GenerationPipeline.js:39`、`:50`、`:155`、`:296` |
| 服务队列等待 | 队列创建时初始化 `lastActivityAt`；任何成功 enqueue 更新；每次 dequeue 用 idle 减去上次队列活动后的时间 | real 上游流使用 `streamTimeoutMs` 默认 60,000 毫秒；等待 headers、首个 chunk 或后续 chunk 时均可能先触发 | `src/utils/ConfigLoader.js:81`；`src/utils/MessageQueue.js:47`、`:53`、`:144`；`src/core/GenerationPipeline.js:312`、`:322` |

| 服务错误归一化 | 队列 `QUEUE_TIMEOUT` 与浏览器 `read_timeout` 走不同入口 | 终止帧前队列超时及浏览器读取超时均归为 `upstream_idle_timeout`，公开消息相同 | `src/core/GenerationPipeline.js:11`、`:333`；`src/core/GenerationError.js:3` |

因此，300 秒前输出预算并不会自动覆盖队列或浏览器的 idle 预算。只要 real 流在响应提交前某段没有队列活动 / body 读取结果，较短 idle 就可能先结束请求。头部和思考等原始流活动可以刷新队列 idle，但未必构成可交付的有效普通正文；二者的超时定义不同。

源码还有一个需明确的重试限制：`GenerationPipeline.js:342` 仅把真正上游 HTTP 错误标为 `upstreamHttp`；`:412` / `:420` 的瞬时错误重试要求该标记。本地队列超时、浏览器 `read_timeout`、网络或队列关闭造成的 `transport_error` 不会仅因映射成 502/504 就获得这一 HTTP 重试资格。因此 `maxRetries=3` 不能解释为每个本地 idle 都自动重试三次。其他空回复重试、尚未发送的 not_dispatched 以及响应是否提交仍有独立条件。

### 11.3 诊断缺口与后续验证

## 13. 三个上下文配置的实际含义与并发风险证据

### 13.1 状态计数、BrowserContext 与浏览器进程

管理状态的 `activeContextsCount` 在 `ManagementAccountService.js:606` 直接取 `browserManager.contexts.size`；旧状态接口 `StatusRoutes.js:1269` 同样取这个 Map 的大小。`BrowserManager.js:2406` 先调用主浏览器的 `newContext()`、`:2421` 创建 page，登录与 WebSocket 初始化后才在 `:2539` 把 `{context,page,...}` 放入 Map。**计数表示已登记的账号上下文项；不包含 `initializingContexts`，也没有逐项确认此刻页面、WebSocket 或上游模型都健康。** readiness 在管理状态中只要求至少一个可用账号连接就绪，不证明全部 Map 项能接收请求。

### 13.2 为什么配置为 3 仍可登记 5–7 个

普通预加载与 standby 初始化有 occupancy 检查：`BrowserManager.js:1891` / `:2127` 将已登记与正在初始化项相加，在池满且未获临时溢出选项时拒绝新增，并在 await 前预留初始化槽位。但替换路径 **明确采用不同策略**：

1. `replaceContextForAuth` 的 `:2162` 用池 mutation 锁串行执行；`:2178` 设置 `allowTemporaryOverflow:true`，先把目标账号初始化成功，再处理源账号。
2. `:2194` 调用 `_closeContextForPoolIfPossible`；若源账号仍有消息队列，`:1795` / `:1787` 只登记 `pendingContextClosures`，暂时保留原 Context，以免切断在途请求。
3. 初始化替换操作完成后锁释放，源账号排空可以发生在之后；再次替换仍可能新增目标 Context。前次待关闭源尚在池中，所以串行替换不等同于最多额外一个 Context 的硬限制。
4. `preCleanupForSwitch` 在 `:2083` 也明确允许忙账号排空期间临时超过 MAX_CONTEXTS。正常队列删除后，`ConnectionRegistry.js:628` 发起 drain 检查，由 `BrowserManager.js:179` / `:1804` 尝试关闭待排空 Context。当前账号、仍有队列或系统忙等条件会影响回收时点。

这证明代码设计允许轮换重叠，**`maxContexts=3` 不是所有时刻实际 Context 数≤3的硬约束**。本轮没有逐次初始化 / 替换 / 排空日志，不能把每次超出都归因于某个替换分支，也不能证明新增数全部是合理的短暂重叠。路由可用性与关闭队列还需联查，不能仅凭 Map 增长给出泄漏结论。

### 15.3 403与429处理差异：已证实机制和未证实原因

本节相关 `GenerationPipeline.js`、`RequestHandler.js`、`GenerationResponseWriter.js`、`ManagementAccountService.js` 与本地HEAD `4cb7756b2c4454d5e3d8586478d65ed4dc74298a` 无未提交差异，与部署元数据对应；本轮未修改服务实现。

1. **生成403被当作带模型作用域的错误。** `GenerationPipeline.js:440` 传 `{message,modelName:model,status}` 给 `_autoDisableAccountForStatus`。`RequestHandler.js:1034` 对status403且有modelName、没有显式accountLevel=true的情况直接return false，特意保留账号供其他模型使用。即使线上 `autoDisableStatusCodes=[401,403]`，此分支也不会按全账号403禁用；页面/账号探测不带modelName或显式accountLevel的403仍可走后面的禁用与清理逻辑。保留全账号启用本身是已设计行为，不能单凭enabled=true认定自动禁用失效。
2. **该分支没有对应的同模型403隔离。** 403返回false前没有写模型冷却或权限拒绝缓存；`GenerationPipeline.js:442` 仅对429调用 `_markAccount429ForModel`。选择器 `RequestHandler.js:353`–`:356` 筛选账号不可用、crash-loop、usage阈值及账号/模型cooldown，没有独立的403模型拒绝筛选。这是具体源码风险：当403确由该账号无法使用指定模型造成，后续独立同模型请求仍可能选到它。**尚未证明本轮40/38条就是这一风险触发的持续新准入**，也没有证明真实403全属于模型权限错误。
3. **403请求仍存在换号重试路径。** pipeline的`:412`将上游403列为可重试状态；在响应未提交、无工具风险、尝试/总deadline未耗尽等条件下，`:425`还要求已派发且未EOF的旧attempt在最多2秒等待内结束。条件满足时，`:446`结合 `_shouldSwitchImmediatelyForStatus` 可进入请求级换号；线上autoDisable列表含403，因此满足立即切换配置判定。`RequestHandler.js:2219` 排除源账号与该请求已尝试账号，优先选择其他已就绪连接。**有这段代码不证明本批每条403都执行过重试**；重试资格、旧attempt完成确认、替代账号与剩余预算均缺运行日志。
4. **最终失败时的重新绑定不等于已重试成功。** pipeline的`:458`调用 `_handleRequestFailureScoped`，该方法可能把请求绑定到另一账号并返回switch结果；当前最终失败分支随后仍调用writer.fail，没有因此开始下一次生成。不能把这次状态或binding变更当作已经完成的成功换号请求。
5. **429有明确的模型冷却保护。** `RequestHandler.js:949`按该模型命中次数设置指数退避、尊重传入Retry-After并受最大冷却限制，写modelCooldowns与lastStatus；`:353`–`:356`和`:2096`–`:2102`分别在选择与派发准备阶段排除冷却账号。立即重试的`:2221`可预热备用账号，`:2238`无替代账号时明确禁止429回落到全局切换器重新选中同一来源。生成pipeline的这条路径主要是模型冷却，不应与其他旧调用路径的全账号quota-disable混为同一种行为。本轮模型请求没有429，**只确认源码保护存在，未完成线上实测验收**。
6. **上游Retry-After尚未接入这条生成错误路径。** helper `RequestHandler.js:938`能解析details中的retryAfter/retry_after数字，但pipeline的`:440`只传message/modelName/status，没有从response_headers提取Retry-After。因此不能宣称当前生成429冷却已遵守真实上游Retry-After；这里可确认的是按配置与命中次数退避，需后续补传递并验证HTTP日期/秒数等格式。

当前可直接提出的后续改善是：先保存脱敏上游error reason/body结构，区分账号级403、模型级拒绝和暂时性403；对已确认模型级拒绝增加有期限的账号+模型不可用状态，路由、备用预热和派发前复查一致使用，同时保留其他模型能力。暂时性拒绝使用可恢复冷却，禁止未经分类将所有403永久禁用全账号。通过本地fixture复现“一个账号某模型403、其他模型正常”“多个请求已在途”“换号无替代账号”“冷却后恢复”等场景，再进行另行授权的线上复测。

### 15.4 最终账号关联覆盖率与attempt证据缺口

`UsageStatsService.js:188`内部记录attemptCount与attempts，`GenerationPipeline.js:180` / `:185`也写逐attempt结果；但 `ManagementAccountService.js:632`–`:653` 的公开usage摘要仅映射finalAuthIndex（必要时回退initialAuthIndex），返回最终outcome/statusCode，不返回attemptCount、attemptId、初始账号或尝试列表。压测采集通道因而无法还原实际换号链。线上maxRetries=3在pipeline的`:110` / `:419`表示最多3次attempt总数，不能由配置推断每条失败实际尝试了3次。
